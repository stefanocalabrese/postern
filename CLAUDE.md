## ⚠️ EVERY OPERATOR MUST DO THESE THINGS THEMSELVES — NOTHING HERE IS DONE FOR YOU

This repo is a **framework**, not a turnkey deployment. Every company that wants to run Postern must implement the items below in their own infrastructure, their own repos, and their own teams. **None of these are optional.** If you skip any of them, the zero-trust guarantees do not hold.

### 1. Backend domain service subject enforcement (ZT-2 — CRITICAL PATH)
**You must audit every handler in your backend services.** Each one must scope queries by the JWT `sub` claim, not by any request body field. If a handler accepts an account ID from the request instead of deriving it from the token, cross-customer data access (A5) is live. This is not a code change in this repo — it lives in your backend repos. **Answer this before writing any other ZT control.** If the domain services don't enforce on `sub`, nothing else matters.

**And they must answer 404, not 403, for another customer's resource.** `stub/backend.py` and `dev-docs/postern-zero-trust-plan.md` section 3.2 require it: a 403 for a foreign ref and a 404 for an unknown one is an account-existence oracle (A5). `services/api/tools/not_found.py` maps both statuses to the same `not found` for the model, and `payments.create_payment` maps both to `account not found` or `payee not found` for its two refs, so a non-conforming backend does not reach the model through the tool, but it is still visible to anything else that sees the backend's answers, and the contract is yours.

**And they own the delegation token's replay check, which is on no other list.** The internal JWT this server mints is replay-protected by nothing here and cannot be: an issuer sees a token once, at creation, and never learns what happened to it. Detecting a second presentation is the recipient's job, so it belongs in your Istio gateway or your domain services, tracking `jti` values they have accepted. `JtiReplayCache` in this repository is not that control despite its name — it is fed a `uuid4` this same process generated three statements earlier, so it detects a UUID collision. Decision record 0014 has the argument. Answer this in the same week as `sub` enforcement; they are the same conversation with the same team.

**And the write endpoint owns durability.** The write endpoint must make the operation durable BEFORE it sends the status line, and must answer 2xx only for an operation it has committed. Confirm closes the connection after reading the status line and never reads the body; a response is acknowledged only by its status, so a backend that commits after streaming its response, or rolls back on disconnect, leaves confirm recording `executed` for money that did not move. The `Idempotency-Key` header carries the challenge id: de-duplicate on it. A call that gets no status line within 30 seconds (`WRITE_TOTAL_TIMEOUT_SECONDS`), a `101`, or a `201` whose header block the parser refuses (for example `Transfer-Encoding: gzip, chunked`) is a transport failure: a 500, the row left `approved`, possibly with the write accepted. Reconcile by `Idempotency-Key`. `docs/user-guide/components/confirm-service.md` has the edge cases.

### 6. Vault transit signing (mostly done here; the deployment half is yours)

**What this repository now does.** `KeySource` is a signing CAPABILITY, not a key: `sign(claims) -> str`, never `signing_key() -> RSAKey`. Set `POSTERN_VAULT_ADDR` and `choose_key_source` builds a `VaultTransitKeySource`, which signs through `POST /v1/<mount>/sign/<key>`. The private key is generated inside Vault and there is no request that returns it: measured against Vault 1.20.4, `GET /v1/transit/export/signing-key/<name>` answers **HTTP 400, "private key material is not exportable"**, to the **root** token. Not 403 from a policy you could widen. `docker compose up` brings a dev-mode Vault with three keys, two policies and two scoped tokens, and `tests/test_vault_live.py` runs 27 tests against a real Vault inside `make ci`.

The PEM and generated branches are unchanged and still supported. `POSTERN_VAULT_ADDR` unset is the absence of a Vault, not a degraded mode. A Vault address **and** a PEM path together is refused at startup, because a PEM still on disk is still what an RCE finds.

**What you must still do.**

- **A real Vault.** Dev mode is in-memory storage, auto-unseal and a known root token. You owe storage, unseal and operations.
- **Three transit keys** (read, write, session), `rsa-2048` or `rsa-4096`, created WITHOUT `exportable=true`. An exportable key answers that export 200 and this whole control is off.
- **Two policies, and they are the read/write split.** No wildcards, no `transit/*`, nothing on `transit/export/*`. The api's policy carries the read key only; confirm's carries the write key and the session key, and nothing on the read key since the layer-1 session token. Do not raise a session key's `min_available_version` past a version whose 10-minute access tokens may still be in flight.
- **Take the read key out of confirm's deployment.** Confirm reads no read-key variable since the session token, so a leftover `POSTERN_READ_KEY_PEM_PATH` mount is ignored at startup and is still a private key on disk that an RCE in confirm finds. Remove any read PEM mount from confirm's task definition, and remove `transit/sign/<read key>` from confirm's Vault policy if an earlier policy granted it.
- **Know what guards the session key against being the read key.** Confirm compares its session key with its write key only, and refuses a match; it no longer holds the read key, so it cannot refuse a session key that is the api's read key. Two guards remain. Under Vault, confirm's token policy grants no path on the read key, so naming it as `POSTERN_VAULT_SESSION_KEY_NAME` is refused by Vault: the sign call answers 403 (measured in `tests/test_vault_live.py`), and so, by the same policy, does the public-key read `create_confirm_app` makes at startup to compare the session key with the write key, so confirm does not start. That guard is the policy, not this repository: a confirm policy that still carries the read key removes it. Under PEM and Vault alike, the api drops any key from `/session/jwks.json` whose thumbprint equals its own read key, so tokens it signed fail to verify. Neither guard takes a copied read PEM out of confirm's hands.
- **Credentials and TLS for the shared state and the key-set fetch.** `POSTERN_REDIS_URL` holds live device codes and refresh families: a deployment owes `rediss://`, AUTH with a per-service ACL user, and no public exposure. The compose stack has all three since 3 October 2026, as throwaway dev versions: a CA and server certificate generated into named volumes by the `redis-certs` one-shot (nothing committed), `--tls-auth-clients no` (the ACL password is the credential, mutual TLS is not exercised), the `default` user off with `postern_api` and `postern_confirm` limited to the key prefixes and commands their code issues. A third user, `postern_operator`, belongs to the revocation CLI and no service holds it: `docker compose run --rm revoke <verb>` runs that CLI from a one-shot container in the `operator` profile, on the compose network but outside the two services (`dev-redis/users.acl`, derived in `docs/user-guide/components/session-store.md` and driven by `tests/test_redis_acl_users.py`), and no `ports:` mapping on `redis`. The passwords are plaintext in the compose file and the ACL file. Both service users hold `+config|get` so the startup preflight can read `maxmemory-policy`; Redis 7 cannot narrow that to one parameter (`+config|get|maxmemory-policy` is rejected), so each can run `CONFIG GET *`, which returns `masterauth` and `tls-key-file-pass` in clear on a deployment that sets them. Grant it only if you keep the preflight's policy check, or deny it and rely on the unverifiable-config warning path. The api's `POSTERN_JWKS_URI` fetch must be HTTPS outside a local stack: whoever can answer it can plant a key and forge any customer's session token. The compose stack fetches it over plain HTTP.
- **Clock skew under 2 seconds between the confirm host and the Redis the revocation store uses.** Run NTP or chrony on both and monitor the offset. Two tolerances compare confirm's clock with Redis `TIME`: `APPROVAL_CLOCK_TOLERANCE_MS` in `services/confirm/device_auth.py` and `PAIR_IAT_TOLERANCE_MS` in `packages/postern-core/src/postern_core/auth/revocation.py`, both 2000 ms. Beyond 2 s a revocation stamp can miss an approval it should refuse, and tokens minted just before a per-pair or per-client (kill-switch) stamp pass the api's floor, so a restore revives them. Both services now REFUSE TO START when `POSTERN_REDIS_URL` is set and the measured skew (one `TIME` call, round trip allowed for) is past 2000 ms (`postern_core.auth.redis_preflight`, no opt-out). That is a check at boot only: drift after boot is not detected, so the NTP monitor stays yours. The same module also refuses to start unless `maxmemory-policy` is `noeviction`; where the server refuses `CONFIG` (managed Redis often does) it logs one warning and starts, so verify that setting by hand there. Confirm against Postgres is a separate, weaker check: it only warns, at 5.0 s, where the Redis preflight refuses to start (item 13, "Read the startup clock warning"). Accept the startup failure mode: with `POSTERN_REDIS_URL` set, Redis must be reachable before either service will start (connection refused fails in about 0.02 s, a blackholed host after the 5 s socket timeout, once per worker process), so deploy Redis before the services.
- **An auth method, not a static token.** Kubernetes, AWS IAM or AppRole, one role per service. A Vault Agent renders the token to a file and `POSTERN_VAULT_TOKEN_PATH` names it; the file is re-read on every call, so a renewal is picked up without a restart. `POSTERN_VAULT_TOKEN` is the local-work escape hatch and does not belong in a deployment.
- **A Vault audit device.** Every signature is now a Vault request, which is the only record of the signing path a compromised process cannot edit. The compose stack's `vault-init` enables a `file` audit device writing to `/vault/logs/audit.log` on a named volume, which is dev-grade (same host as the Vault it audits, no rotation, no shipping, no retention, and dev mode's root token can disable it); this repository ships nothing for a deployment's own device.
- **A rotation cadence.** The published kid carries the version and every version Vault holds is published, so pre-rotation tokens keep verifying and verifiers pick the new key up on their next JWKS fetch, within `POSTERN_VAULT_PUBLIC_KEY_TTL_SECONDS` (default 300). Do not raise `min_available_version` past a version whose 60-second tokens are still in flight.
- **Budget the latency.** Measured on loopback, a transit signature is 1777µs against 926µs in process, and a `tools/call` moved p50 4.3ms to 5.7ms over a container network. `POSTERN_VAULT_TIMEOUT_SECONDS` applies per phase, so one call's worst case is four times it, and `POSTERN_REQUEST_DEADLINE_SECONDS` carries four times it as a term.
- **Accept the startup failure mode.** Vault unreachable at startup means the container never becomes ready, by design — that keeps the previous task set serving instead of routing traffic to a pod that 500s every call. There is no flag that turns it off.

**Be clear about what this buys.** The signing key is no longer stealable and the signing capability is revocable, time-boxed and observable. An attacker with RCE in the api container still mints read tokens for any customer while they hold the process, because `sub` comes from the caller. Whether such a token returns another customer's data is item 1 (ZT-2), and it is still owed.

### 11. A database role that owns nothing (the `audit_log` append-only control)

Migration `f1860c110112` makes `UPDATE`, `DELETE` and `TRUNCATE` on `audit_log` raise for every role. **A trigger is only as strong as the privileges of whoever can turn it off**, and until 29 September 2026 one role in every environment here was simultaneously the table owner, the role migrations ran as, and a superuser — two statements from the control being off, performed rather than described in `tests/test_audit_append_only.py`.

**This repository now ships the split, and `docker compose up` uses it.** Two SQL scripts carry it: `sql/01-roles.sql` (a superuser runs it once per database, before migrations) and `sql/02-grants.sql` (`postern_owner` runs it after every migration). `docker-compose.yml` runs both, and `tests/conftest.py` reads the same two files off disk and executes them, so what the suite measures and what the stack applies cannot drift. Decision record 0019 carries why they are scripts and not a migration.

Three roles:

- **A bootstrap superuser**, which creates the other two and does nothing else.
- **`postern_owner`**, which owns every table and runs `alembic upgrade`. No service connects as it.
- **`postern_app`**, which owns nothing, is not a superuser, and holds exactly `SELECT, INSERT` on `audit_log`, `SELECT` on `consents`, `SELECT, INSERT, UPDATE` on `challenges`, `USAGE` on the `audit_log` and `challenges` sequences, `USAGE` on schema `public` and `CONNECT` on the database — and **nothing on `alembic_version`, and no `CREATE` on the schema**. Both services connect as this one via `POSTERN_DATABASE_URL`. No new variable: the split is three values of one.

The grant set is derived from the three store modules rather than listed, and `tests/test_application_role.py` carries the derivation. Two parts are worth knowing: `SELECT` on `audit_log` is **load-bearing on the write path**, because the ORM emits `INSERT … RETURNING id` and decision 0006 makes a failed audit write a failed tool call; and nothing in either service reads `alembic_version` or writes a `consents` row.

**What an operator still owes, and it is the whole of it: real credentials.** Both scripts create the roles able to log in and unable to authenticate — no password lives in this repository. Set them from your secrets manager, point `migrate` at the owner and both services at the application role, and keep the owner's and the superuser's credentials unreachable from the serving containers. A credential in the application's environment makes the split buy nothing.

**What you get for it, measured** (`tests/test_audit_append_only.py`, 16 tests; `tests/test_application_role.py`, 13 tests, both against `postgres:17-alpine` inside `make ci`): the application role appends and reads normally and drives a whole approval — challenge created, claimed, transitioned to `executed`, both audit rows written — while `UPDATE`, `DELETE` and `TRUNCATE` are refused **at the ACL check, before the trigger is consulted** (`permission denied for table audit_log`, asserted alongside the *absence* of the trigger's own text), and it cannot disable the triggers, drop them, drop the table, set `session_replication_role`, or create a table to own. Re-run from inside the running `api` container: nine of ten statements refused. The tenth, `GRANT DELETE ON audit_log TO CURRENT_USER`, returns a success tag and grants nothing — PostgreSQL answers a grant-option-less GRANT with a warning. A probe watching only for exceptions would record that as the bypass that worked.

**The owner bypass costs three statements now, not two.** `f1860c110112`'s `REVOKE … FROM CURRENT_USER` was decorative while `CURRENT_USER` was a superuser; it is `postern_owner` now, so the owner must grant the privilege back to itself first. Three statements is not a wall, it is a receipt — keep the application off that role.

**If you run the application as an owner or a superuser anyway**, `audit_log` is protected against an attacker who can run one statement and not against one who can run two or three. The write path's rows, the only record that a payment approval happened at all, are in that second category.

Three things the split does not give you, in any configuration. **No confidentiality:** the application role still reads every row of all three tables, unscoped by customer, and still appends arbitrary rows to `audit_log` — it must, because decision 0006 makes a failed audit write a failed tool call. **No detection:** a `DELETE` that matches no row succeeds silently, a refused one records nothing, and the raise aborts the transaction the record would have been written in. It is a wall, not a tripwire. **No defence against a superuser:** nothing in a database binds one.

### 12. The payments producer flag (`POSTERN_PAYMENTS_ENABLED`)
- **Leave it off in production.** It registers `payments.create_payment` and `payments.get_payment_status` on `services/api`. Turn it on only when both hold, and after item 13: a delivery path shows the stored challenge on the customer's phone; and a consent-grant flow can write a `payments` consent row (today a row has to be written by hand).
- **What it changes when on.** The two tools are registered, always behind the `payments` consent check, so a client without that consent row neither lists nor calls them. With the flag on, `start_session`'s confirmation note says that if payment tools are listed they only propose a payment, which the customer approves in their banking app and never in the conversation. Nothing else on the read surface changes (`tests/test_tool_surface_golden.py`, `tests/test_no_write_from_api.py`).
- **What an RCE in the api gains with it on.** Nothing the shared `postern_app` grant did not already allow: it can insert and expire pending challenges for any customer. It still cannot approve (an enrolled device signature and a banking-app assertion are needed) or execute (the write key is not in the process). Decision record 0022 records the api-side `pending` to `expired` update this needs.
- **Your payments backend owes two things.** `GET /payees/{ref}`, scoped by the internal token's `sub`, answering `payee_ref` and `name` and no account number, under scope `payments:read`; and `POST /payments` accepting the stored payload as its body, `payee_name` included, under `payments:execute` only.
- **Your gateway must check key and scope per path.** `payments.svc` is now an audience the api's READ key can mint, with scope `payments:read` (decision 0022). Read/write separation at `payments.svc` depends on your gateway validating the signing key and the scope per path: a `payments:read` token from the read key must not reach `POST /payments`, or the separation this repository enforces by key is gone.

### 13. Tier-2 approval proof (`POSTERN_CONFIRM_IDV_VALUE`)
- **Set `POSTERN_CONFIRM_IDV_VALUE` on `services/confirm`** to a value agreed with your banking-app backend: 1 to 128 printable ASCII characters, emitted in no other claim. Unset, confirm starts with one warning and refuses every tier-2 approval (`verification_required`); every payment is tier 2, so that is every payment.
- **Make your app backend meet the contract** in `docs/integration/mobile-app-pairing-contract.md` section 12: for a tier-2 approval, the assertion carries `idv`, `challenge_id`, a unique `jti` and `auth_time`, set only from the backend's own record of an identity verification that completed for that challenge and that customer, never from the app and never from the login session, and at most one assertion per verification.
- **Know what it does not prove.** Confirm checks that those claims are present and consistent; it cannot check that the selfie match happened, that it happened after the challenge, or that one verification backs only one assertion. A compromised app backend or a stolen assertion-signing key mints the claims for any challenge. Decision record 0023 records that trade, and a signed attestation from the identity-verification service is the stronger form it leaves open.
- **Keep three clocks within a few seconds.** Confirm checks `auth_time` against the challenge's `created_at`, which is Postgres's `statement_timestamp()` stored when the row was created (lower bound, 30 seconds of slack), and against its own `time.time()` (upper bound, 30 seconds of slack), while the app backend sets `auth_time` from its own clock. If confirm's clock lags the app backend's by more than about 30 seconds, or the database's clock leads the backend's by more than about 30 seconds, legitimate tier-2 approvals are refused: a liveness failure, not a safety one. Run NTP on the app backend, confirm and Postgres.
- **Read the startup clock warning, and do not wait for it to stop the service.** In its lifespan confirm runs one `SELECT statement_timestamp()` (the clock that stamps `created_at`) through its own database engine, bounded by a 1.0 s query timeout and a 1.5 s bound on the whole check, connect included (`services/confirm/database_clock.py`). If the skew between confirm and Postgres (database minus confirm, taken at the midpoint of the round trip) exceeds 5.0 s either way, it logs one WARNING on logger `services.confirm.database_clock` with the direction: database ahead, legitimate tier-2 approvals may be refused as the skew nears the 30 s window; database behind, the `auth_time` freshness window is widened by that much. A check that cannot be measured (database unreachable, query timed out, answer not a timezone-aware datetime) logs one WARNING saying so. It never blocks startup, runs once per worker process and at boot only, so drift after boot is not detected and the NTP monitor stays yours. Alert on that logger.
- **Alert on `audit_log.detail = 'tier_mismatch'`.** No path in this repository writes a row below its operation's declared tier, so one is what a compromise of a process holding `postern_app` leaves behind.
- **An approval returns no exception text.** The claim's `except` answers the fixed 500 `internal_error` "the approval could not be recorded", and the `resolve_endpoint` `ValueError` branch the fixed 500 "the approved operation could not be set up"; the audit row's `detail` and the log lines carry the exception type only. Before that, a driver error's SQL and bound parameters reached the response description. The 207 follows the same rule: its `message` is the fixed text "approval recorded, backend execution failed" plus the numeric `backend_status`, and no text the backend sent reaches the response, the audit rows, an application log line or an exception message (one WARNING per refusal carries the challenge id, the operation and the status). The backend's response body is never read, only its status line (the request is streamed and closed after the status), so an accepted 200, 201 or 202 with an undecodable body is still an accepted write; a failure before any status is reported by exception type name only (`BackendTransportError.kind`, the original not chained) and is answered 502 `{"execution": "outcome_unknown"}` with a fixed body, the row left `approved`, no retry, and the completion audit row `raised` with the original kind, so the app can tell "the payment may have been made" from an internal crash (`tests/test_outcome_unknown.py`), and `httpx2` and `httpcore2` are held at WARNING in both services.
- **A SQL driver error is kept out of the client's reply and out of log records, by four layers, within the limits listed under Known limits.** (1) Both `Database` engines and `migrations/env.py` set `hide_parameters=True`, and `migrations/env.py` also installs the record factory after `fileConfig` and replaces a driver error that escapes `alembic upgrade` with a fixed `RuntimeError("migration failed: <type and SQLSTATE>...")`, raised outside the `except` so no cause or traceback of the original is printed (an error that is not a driver error passes through untouched; the operator reads the statement and DETAIL in Postgres' own log). (2) `services/api` builds `FastMCP` with `mask_error_details=True`, so an exception a tool raises other than a `ToolError` reaches the client as `Error calling tool 'x'` with no detail (a `ToolError` is re-raised unchanged, so the tools' own fixed refusals still arrive), and `AuditMiddleware` replaces EVERY exception that leaves `on_call_tool` and is not on its allowlist (`FastMCPError`, `NotFoundError`, `DisabledError`, `MCPError`, `RevokedError`, `RiskActionError`, `RevocationStoreUnavailable`, `SessionStoreUnavailable`, and a bare single-sentence `PermissionError`) with a JSON-RPC error `-32603 internal error` (the call still fails closed; a driver error, the text of an unlisted class such as a Redis `ConnectionError` carrying a URL with a password, and a wrapper whose text embeds the driver's all reach the client as that one fixed text), which is the layer that covers the completion-row failure, since that one leaves as a JSON-RPC `error.message` that masking does not touch. The reply shape of a driver error below the middleware has moved twice: before 287d216 it reached the client with the driver text inside it, from 287d216 it was an `isError` `ToolError` with fixed text, and since 7eac0c9 it is a protocol-level JSON-RPC `-32603` error. That last move is deliberate and has a cost: the MCP 2026-07-28 tools page (fetched 7 October 2026) files server errors under protocol errors, says clients MAY pass protocol errors to the language model and that they SHOULD pass tool execution errors, so a client may never show the model that the call failed, where an `isError` result would have been shown. (3) `postern_core.log_safety.install_sql_safe_logging()`, called by both app factories, wraps the process-wide log record factory, so a record created through `Logger._log` on any logger and handler (uvicorn, FastMCP's own handler, the MCP dispatcher, asyncio, SQLAlchemy, root) is sanitised when created: an `exc_info`, an argument or a message that is an exception, or sits anywhere inside the arguments within the scan's bounds (an iterative walk with a 2,000-item budget and a 20-level depth cap, over nested tuples, lists, sets, frozensets, deques and dicts, keys and values; an object's `__dict__` or `__slots__`, entered with `object.__getattribute__` only, so no `__str__`, `__repr__`, `__getattr__` or `__iter__` of an unknown object runs, and the object is replaced whole by `<Type holding a driver error: ...>`; and the `args` of a non-driver exception), an `extra=` attribute (`Logger.makeRecord` is wrapped) or a record built by `logging.makeLogRecord` (wrapped), whose chain (cause, context, exception groups) holds a SQLAlchemy `StatementError` or an asyncpg exception becomes the traceback frames plus one line per exception with its type and SQLSTATE, `client-side` for an error asyncpg raised without a server, and a literal saying the message, SQL and parameters were withheld; `warnings.warn` goes through the `py.warnings` logger (`captureWarnings`, installed by the same call) and the message of a SQLAlchemy warning is withheld, category, file and line kept; it also pins `sqlalchemy.engine` and `sqlalchemy.pool` at WARNING, because the engine logger writes result rows at DEBUG. The suite replaces the warning half with a no-op in the pytest process (`tests/conftest.py`), because installing it inside a test would move that test's warnings from pytest's summary to the log; it is exercised by calling `_showwarning` directly and by a subprocess in `tests/test_sql_safe_logging_reach.py`. (4) The application's own log calls log `describe_exception(exc)` and pass `exc_info_for_log(exc)`, so they do not rely on (3); `tests/test_log_call_scan.py` scans `services/` and `packages/` by `ast` and fails on a log call of the shapes it recognises (see Known limits) that hands a handled exception to a logger, unless that exact call is allowlisted with a reason; the flagged set and the allowlist must be equal, so a new unsafe call in an allowlisted function fails and so does a listed call that disappeared. `tests/test_device_code_log_handles.py` adds a second scan: no logger call in `postern_core/auth/` or `services/confirm/` passes a value named `device_code`, `user_code`, `refresh_token`, `token` or `secret` except through the handle function, because a device code is a bearer credential (it is the whole authority to exchange at `POST /token`) and a log outlives its 900-second life. THE RULE FOR A DEVELOPER: never pass `str(e)`, `repr(e)` or an f-string of a driver error to a logger, and do not call `logger.exception` or pass `exc_info=True` where the handled exception may be one: use `describe_exception(e)` and `exc_info=exc_info_for_log(e)`. A backend 404 or 403 on a caller-chosen account ref (`accounts.get_balance`, `transactions.list`) reaches the model as the fixed `not found`, identical for a foreign and an unknown ref whatever the backend answers; a backend 400, 401, 500 or 503 and a failure to reach the backend stay `Error calling tool 'x'`, except that FastMCP words a raw timeout and an HTTP 429 as its own fixed sentences (`Upstream request timed out, please retry`, `Rate limited by upstream API, please retry later`), with nothing from the backend's body in either. What would remove (3): code that calls `logging.setLogRecordFactory` after the app is built with a factory that does not chain to the previous one; `dictConfig` removes handlers, not the factory, and any ASGI server keeps it. For an error Postgres raised, its own log has the message, the DETAIL and the statement at the same time (with `log_min_error_statement` at its default `error`; to match on a SQLSTATE put `%e` in `log_line_prefix`, the default `%m [%p] ` carries none). Errors asyncpg raises in the client while encoding a parameter (for example `DataError`, "invalid input for query argument") never reach the server and leave no record anywhere; the sanitised line says `client-side` for them. Postgres' log then holds the values these logs withhold (DETAIL `Failing row contains (...)`): treat it as customer data.
- **The approval body is validated before the claim (step 2d).** After the revocation, ownership, signature and tier checks and before the claim: `confirming_device` must be a string of 1 to 128 characters, and for tier-1 rows `verification_result` must be a string (a tier-2 row ignores it and stores the assertion's `jti`); neither may contain a Unicode control, format or line-separator character (categories `C*`, `Zl`, `Zp`), and an absent or `null` field passes. A violation is 400 `invalid_request` with a fixed description naming only the field, audit `detail` `body_field_invalid`, and the row stays `pending`. Because the check precedes the claim's status and deadline test, an expired row with a bad body answers 400 and is not retired, and an executed row answers 400, not 409. JSON `NaN`, `Infinity` and `-Infinity` in the body are refused at parse time as 400 `malformed_body` with an audit row, and `clip_tree` (`postern_core/store/audit.py`) turns non-finite floats into strings so an audit row cannot fail on one. A non-string `signature` is 400 `missing_signature`; a path challenge id outside `[A-Za-z0-9_-]{1,36}` gets the unknown-id 404 with an audit row.
- **Every JSON body confirm and api parse is read with the strict parser.** `postern_core.json_strict.loads_finite` (str) and `loads_finite_utf8` (request bodies: strict UTF-8, no BOM, so UTF-16, UTF-32, a UTF-8 BOM and raw surrogate bytes, all of which `json.loads(bytes)` accepts, are refused) refuse `NaN`, `Infinity`, `-Infinity` and an overflowing literal such as `1e999` as malformed, so a non-finite number reaches no handler and no audit row: the approval callback and the three device-grant routes that read JSON (`/device_authorization`, `/scan`, `/approve`; `/token` reads a form) answer their own malformed-body 400, and the api's header/body validation answers 400 with JSON-RPC `-32700` for ANY body it cannot parse strictly (not only a non-finite one) before FastMCP sees it, so a difference between the two parsers cannot matter. It does so on EVERY POST path of the api, before authentication (instead of the 405, 404 or 401 a route would give, like its 413 and `-32020` refusals), so a future form-encoded POST route on the api must be exempted explicitly. The same walk refuses, with the same answer, a body holding a string with U+0000 or a surrogate anywhere (the `id`, `arguments` and `_meta` included) or over 1,000,000 nodes, because such a call used to fail its audit insert and end as a 200 with no row; nesting depth is not refused, and `scrub_tree` records `"[nested too deeply]"` past 100 containers so the audit row is still written.
- **Known limits, each measured against the tree and none closed here.**
  - Exception text that does not go through `logging` is not covered: an OpenTelemetry exporter or a Sentry-style SDK that records the exception object bypasses the record factory (FastMCP's telemetry calls `span.record_exception(e)` and `set_status(str(e))`). None is configured here, and `tests/test_no_exception_exporters.py` fails if an OpenTelemetry SDK or exporter, `sentry_sdk`, `ddtrace` or `elasticapm` is importable or appears in `uv.lock`, if the Dockerfile or `docker-compose.yml` sets an `OTEL_`, `SENTRY_`, `DD_TRACE` or `ELASTIC_APM` variable, or if FastMCP's tracer provider stops being OpenTelemetry's non-recording default: enabling an exporter needs a scrubber first. `OTEL_SDK_DISABLED=true` was not added to the Dockerfile, because it disables an SDK that is not installed and would have to be carved out of that test. Text an application already built into a message string with an f-string is also out of reach, except the `repr` asyncio embeds for an unretrieved task exception, which the factory replaces.
  - The log-call scan (`tests/test_log_call_scan.py`) is heuristic. It matches a receiver named with `log`, a `getLogger(...)` call, or any name or attribute assigned in the module from `logging.getLogger`, `logging.Logger`, `structlog.get_logger`, `.getChild(...)`/`.bind(...)` of a logger or another such name (`sink = logging.getLogger(...)`, `self._audit = ...`, `out = sink`), plus `getattr(logger, "error")(...)`, a name imported `from logging import ... as ...`, `warnings.warn`, `print` and `sys.stderr.write`, and it follows `saved = e`, `saved = e.args` and tuple unpacking from the handled exception to the end of the function. It still misses a logger that arrives as a parameter under a name without `log`, an exception carried in a container built earlier, taint across functions, and any helper that logs on the caller's behalf. `str(e)` and f-strings are flagged by the scan and are the one shape the record factory cannot fix.
  - Not covered by the record factory (each measured to leak the sentinel, and each pinned by a test so it is not mistaken for coverage): an exception beyond the scan's 2,000-item budget or 20-level depth cap; a non-chained wrapper whose own text embeds the driver's (`RuntimeError(f"x {e}")` raised outside the handler: nothing links it to the driver error, and matching SQL keywords in strings is deliberately not attempted); `str(e)` passed as an argument or built into an f-string at the call site; a non-dict `Mapping` argument (not entered); a record made by `Logger.handle` or `LogRecord(...)` built by hand; an attribute a custom record factory adds after ours; a handler that reads an exception from a custom attribute after a custom factory replaced ours without chaining; the text of a non-SQLAlchemy warning; and any exception recorded outside `logging` (exporters, above).
  - Read-path and Vault exceptions carry a status or a type name and no backend, transport, Vault or Redis text (`BackendError`, `BackendUnavailableError`, `VaultTransitError`, and the Redis store wrappers re-raise `from None`), so FastMCP's own `logger.exception` has none to write; `tests/test_read_path_exception_text.py` and `tests/test_api_read_path_logs.py` hold it. A Redis connection error raised at startup by the preflight is not wrapped and still names its host and port.
  - A failure during the app's lifespan startup is sent by Starlette as a plain-text traceback message, not through the record factory; it carries whatever the startup code raised. Measured, not closed.
  - After the backend accepts the write, `approved -> executed` is recorded with up to 3 attempts, each on a fresh session, in a background task held in `_BACKGROUND_RECORDS` and awaited through `asyncio.shield` (`_record_executed_detached` in `services/confirm/callback.py`). Measured on uvicorn 0.52.4: under the shipped command (no `--timeout-graceful-shutdown`) shutdown waits for the request, so the record lands and the shield is not used; a client disconnect never cancels a non-streaming handler; with `timeout_graceful_shutdown` set uvicorn cancels the request (one ERROR line, "the request was cancelled while recording it") and then runs the lifespan shutdown, which waits for the recording up to `SHUTDOWN_RECORD_WAIT_SECONDS` (25 s: three attempts at the default timeouts come to 27.4 s, capped under ECS's default 30 s `stopTimeout`, and whether an operator's `stopTimeout` differs is not established) and then cancels and awaits what is still running, inside the lifespan, because under SIGTERM uvicorn restores the default handler after its shutdown and re-raises the signal inside its own coroutine, so the process dies (exit 143) before `asyncio.run` could cancel anything (`tests/test_shutdown_signals.py`, a real subprocess with uvicorn in the main thread; the thread-based `test_real_uvicorn_*` tests never see this). **Budget rule: `timeout_graceful_shutdown + 0.1 + SHUTDOWN_RECORD_WAIT_SECONDS < stopTimeout`**; the wait starts only after uvicorn's graceful phase, so a graceful timeout above about 4.9 s puts SIGKILL before the end of a 25 s wait at the default 30 s. Under the shipped command there is no graceful timeout, uvicorn waits for the request without bound, the lifespan wait never runs, and a SIGKILL at `stopTimeout` can drop a record with no line; a second SIGTERM does not force an exit (uvicorn keeps waiting; only a second SIGINT does). What is lost: a recording still running when that wait ends, and a forced exit (a second SIGINT; uvicorn skips the lifespan shutdown). Both leave the row `approved` and log one ERROR line from the task, "was cancelled before it finished" (the lifespan cancels the first under SIGTERM and SIGINT; `asyncio.run` cancels the second), except when SIGKILL arrives first or the OS kills the process, which log nothing, so the request-side line's promise of a follow-up line is kept in every case but those. The backend is never called again, because no backend dedupe behind the `Idempotency-Key` is documented. If every attempt fails, or the row is not `approved` on the first, the caller gets 202 `accepted_unrecorded` (callers must never retry it), the row is normally still `approved` (not if an attempt landed after all, or something else moved the row; the ERROR line says "could not be confirmed as executed; check the row"), the completion audit row is `raised` with detail `executed_unrecorded` and one ERROR line names the challenge id. An exception escaping the recording task is logged by type and answered with the same 202, not a 500, and the log helper never raises (it falls back to a line with the id alone). The 202 message reads "recording it as executed failed or could not be confirmed" because the row can be `executed` after all. Setting a graceful timeout has a cost: a cancelled approval, one still waiting on the backend, answers the client a bare 500 and writes no completion audit row for a payment the backend may have accepted (measured; predates this section, not closed). What remains: a database outage that outlasts the three attempts still yields the unrecorded 202, or a bare 500 if the completion audit row also fails; process death between the backend POST and the UPDATE leaves `approved` with no response at all; and nothing reconciles any of these automatically, the operator joins `audit_log` by challenge and asks the backend by `Idempotency-Key` = challenge id.
  - Under pool contention the record phase competes with new approvals for the same pool connections. Measured by the reviewer's probe, pool of 2 with 10 concurrent approvals each holding its record connection 1.5 s: 4 answered 500 (backend not called), 4 answered 200 and 2 answered 202, so 2 of the 6 accepted payments ended unrecorded; the connection cap held and everything failed closed. Routing the record through the audit reserve would give money that already moved priority over new approvals, but it changes the reserve semantics of decision 0006, and it is not done.

## What this is

An MCP server exposing an operator's own backend services to external consumer AI clients (Claude, ChatGPT, Perplexity) as tools across four domains: accounts, transactions, cards, payments.

**The operator is the ASPSP, not the TPP.** This inverts almost all public Open Banking prior art, where every project is a third party reading accounts through an aggregator. No inbound TPP certificate verification, no multi-ASPSP adapter layer, no eIDAS certificates presented outbound. Tool contracts borrow Open Banking semantics for familiarity only.

The defining property that drives every decision: an LLM the operator does not control chooses which tools to call, against real money, with attacker-controllable text (transaction memos, payee names, merchant strings) in its context. The operating assumption is not "the network is hostile" but **"the caller is under adversarial influence at all times, even when correctly authenticated."**

## Architecture

Two deployables over one shared library. This is a decision, not a preference (handoff §8.2):

| Service | Holds | Vault role | Can reach |
|---|---|---|---|
| `services/api` | MCP tools | **read** | backend read endpoints only |
| `services/confirm` | OAuth/device-grant endpoints, QR page, approval callback, execution | **write, session** | backend write endpoints |

`packages/postern-core/src/postern_core/` carries `domain/` (masked types), `facade/` (httpx2 + internal JWT), `store/` (SQLAlchemy + Alembic), `auth/` (Vault key fetch, JWT minting), `risk/` (tier selection).

Two authentication layers that must never be conflated (handoff §7.1):
- **Agent to MCP server**: OAuth 2.1, CIMD over deprecated DCR, RFC 8628 device grant with a QR flow.
- **MCP server to backend**: Vault-signed JWT through an Istio ingress gateway over PrivateLink, 60-second expiry, RFC 8693 delegation shape (`sub` = customer, `act.sub` = service).

The read/write Vault key split is what makes "the tool handler cannot reach a backend write endpoint" an infrastructure property rather than a code-review promise. A compromised tool handler cannot mint a token the payments service accepts, because it does not hold the key.

The write path never returns through the model's channel: `create_payment` persists a challenge row and returns a `challenge_id` immediately; the push notification payload is built server-side **from that stored row**; the user approves on their own device; the approval callback (not the tool handler, not the agent) calls the backend write endpoint. An injected agent can propose a wrong payee but cannot change what the user is shown.

## Hard rules

These are decisions carried over from the design conversation. Do not relitigate them in code.

- **No payment execution tool exists.** Only `payments.create_payment` and `payments.get_payment_status`. A `submit_payment` in the schema hands the model an execution capability and makes safety depend on it choosing not to use it. Remove the capability instead.
- **Execution belongs to the approval callback**, never a tool handler. The tool-handler process must not hold the credentials or network permission to reach backend write endpoints.
- **The confirmation payload is built server-side from the stored challenge row**, never from agent input. This is the property that makes prompt injection at tool-call time survivable.
- **Never accept `user_id` as a tool argument** and never hand it to the client. The server derives the customer from the token on every call. A user identifier the model can set is a direct object reference an agent can be talked into changing.
- **Never write "Face ID" anywhere in this codebase or its docs.** The operator's app brands its identity-verification feature that way, but it is server-side selfie matching in the backend cluster, not Apple's on-device feature. Any reader, human or model, will implement the wrong thing. Use "app identity verification"; write "device unlock biometric" when the phone's own biometric is meant.
- **Masking is a type property, not a function someone remembers to call.** `MaskedPan`, `MaskedIban` via `Annotated` + Pydantic validator, whose only constructor masks. A handler that forgets must fail validation, not leak. Prefer the backend returning pre-masked values so the server never holds a full PAN and stays out of PCI DSS scope.
- **A `ValidationError` from a masked type carries the raw PAN or IBAN.** `hide_input_in_errors` covers only `str()` and `repr()` of the exception; its structured `errors()` output and `.json()` still contain the raw offending value by default. Any handler that serializes a masking `ValidationError` toward a client must call `errors(include_input=False)` or `json(include_input=False)`, or the value the type exists to protect leaks through the error instead of the response.
- **`payments.create_payment` takes a `payee_ref`, never a raw IBAN.** A new payee's IBAN is typed in the bank app during confirmation and never passes through the agent channel.
- **`cacheScope` is `"private"`, never `"public"`.** Those are the only two values the spec allows, and `"private"` means "MUST NOT be shared across authorization contexts". The tool catalog varies by consent state; a shared cache leaks which accounts and permissions a customer has. That is a data leak, not a performance bug. `ttlMs` and `cacheScope` are both required fields on `server/discover`, `tools/list`, `prompts/list`, `resources/list`, `resources/templates/list` and `resources/read`.
- **Validate `Mcp-Method` / `Mcp-Name` headers against the body** before any handler runs; mismatch returns 400 with JSON-RPC `-32020`. A load balancer routing on a header while the server executes on the body is a request-smuggling shape. **This must be ASGI middleware, not FastMCP middleware**, for the reason in "Version traps" below.
- **MRTR is for disambiguation only** (which account, which card, which date range). Never for authorizing money movement, because the answer routes back through the model's channel.
- **Tier 1 is the default for writes, not tier 2.** Tier 2 adds server-side identity verification, which is a GDPR Article 9 special-category processing event on every single use, costs 5 to 15 seconds, and fails a real percentage of the time. Tier 1 already satisfies SCA with two factors.
- **Declare the verification tier on the tool definition.** Never derive it from the HTTP verb: search endpoints are POST because the body is large, and a five-year transaction export is a GET.
- **Do not cite network isolation as a zero-trust control.** PrivateLink is blast-radius reduction. The identity layer is the control.
- **Tool definitions are static config versioned in the repo**, never registered at runtime by backend services. Runtime registration breaks the PrivateLink design and makes the tool surface impossible to diff between deploys.
- **Do not map backend endpoints 1:1 to tools.** OpenAPI-to-MCP generators are unusable here: they would expose a directly callable payment endpoint and discard the challenge flow, consent checks, idempotency and audit chain.

## Version traps

Both of these will produce plausible, wrong code from memory. Verify before relying on either.

- **FastMCP is at v4.0.3 (2026-09-05), under the `PrefectHQ` org, not `jlowin`.** Nearly every FastMCP example in training data and on the web is v2 or v3. Docs are in llms.txt format at `https://gofastmcp.com/llms.txt`: fetch the index, then the page. The implementation guide's §0.1 lists what was verified on 12 September 2026; anything outside it is design reasoning, not a verified framework fact.
- **`ToolError` cannot produce an HTTP status.** FastMCP 4 returns it as `CallToolResult(is_error=True)` inside an HTTP **200**, and exposes no documented way to set the status from a tool or a middleware hook. The implementation guide §6.3 shows header/body validation as a FastMCP `Middleware` raising `ToolError`; that is wrong and cannot satisfy the spec's "MUST return 400". Any control that owes an HTTP status belongs in ASGI middleware passed to `http_app(middleware=[...])`. `McpError(code=..., message=...)` sets an arbitrary JSON-RPC code but still not a status.
- **The HTTP client is `httpx2`, not `httpx`.** `fastmcp` 4.0.3 pulls `fastmcp-slim[client,server]`, which declares `httpx2>=2.5.0` and no `httpx`. `respx` cannot mock it: it type-checks against `httpx.Response` and raises `TypeError` at mock-setup time, before any request. Backend tests inject `httpx2.MockTransport(handler)` instead, which does carry an `Authorization` header through to the handler. `respx` has been removed from the dev group. See `dev-docs/decisions/0001-facade-http-client.md`.
- **Smaller v4 facts, all verified:** `@mcp.tool` works bare *and* with parentheses. Tool annotations come from `mcp.types.ToolAnnotations`, not from fastmcp. `ctx.set_state` / `get_state` are **async** (`await`). `FastMCP()` accepts `cache_scope` and `cache_ttl` directly. `Client.__init__` **does** take an `auth` argument in 4.0.3 — checked against the installed package, not recalled — but `FastMCPTransport.__init__` takes only `mcp` and `raise_exceptions`, so under the in-process `Client(transport=server)` there is no validated token and `get_access_token()` returns `None`. That, and not the constructor signature, is why tools resolve the customer through an injected `CustomerResolver` rather than reading the token directly. The phrase "accepts no auth argument" still gives the reason four times on 2 October 2026, once in `services/api/server.py`'s module docstring, twice in `tests/test_audit_entry_row.py` and once in `tests/test_audit_middleware.py`, and each is wrong about the signature and right about the consequence.
- **Package identity:** this project uses `fastmcp` (PrefectHQ, `from fastmcp import FastMCP`), not the official `mcp` SDK (`mcp.server.mcpserver.*`). Mixing imports produces confusing type errors. Pin `fastmcp>=4.0.3,<5`.
- **MCP protocol `2026-07-28` removed the `initialize`/`initialized` handshake and protocol-level sessions**, including `Mcp-Session-Id`. Every request is self-describing and any request can land on any instance. No in-process session state at all: mint an explicit handle and have the model pass it back as an argument, which is exactly what the challenge ID does. Server-level `instructions` now lives on the `server/discover` result. There is a third mandatory header, `MCP-Protocol-Version`, alongside `Mcp-Method` and `Mcp-Name`. SSE resumability is gone, so a dropped stream loses the in-flight request and the client re-issues it with a new id: **every handler must be safe to re-run**. MRTR's `requestState` is attacker-controlled and MUST be integrity-protected (HMAC or AEAD) if it influences authorization.
- **DPoP is not in the spec.** A search of the entire `2026-07-28` tree, security-considerations page included, returns zero hits for DPoP, RFC 9449, sender-constrained tokens or mTLS. The only token-binding mechanism is audience restriction via RFC 8707 resource indicators. This closes ZT-6's first branch: it resolves to a written decision record plus compensating controls, not to implementing DPoP.

## Toolchain gotchas, each found the hard way

- **`.importlinter` needs `root_packages` (plural) listing both `services` and `postern_core`.** With only `services`, import-linter never graphs the shared library, so `services.api -> postern_core -> services.confirm` reports **KEPT with exit 0**. That two-hop route through the one library both services import is the realistic regression path, so the singular form makes the contract decorative.
- **`.python-version` pins 3.12.** Without it `requires-python = ">=3.12"` lets uv resolve 3.13 while mypy targets `python_version = "3.12"`, ruff targets `py312`, and the Dockerfile ships `python:3.12-slim`.
- **`packages/postern-core/src/postern_core/py.typed` is required.** Without the PEP 561 marker, any mypy run that does not pass `packages` and `services` in one invocation degrades to `Skipping analyzing "postern_core"`.
- **`ruff format --check` is scoped to `packages services tests`, never `.`.** Unscoped it also rewrites the Python code fences inside the markdown design docs. Re-measured 2 October 2026, and the size of it is worth knowing: `uv run ruff format --check .` reports 19 files would be reformatted — 18 markdown documents and `migrations/versions/ed88bd4a6312_add_challenges_table.py` — where the scoped form reports 218 files already formatted and nothing to do. **`make fmt` is `ruff format .` and is not scoped**, so it is the target that would actually perform those 19 rewrites; `migrations/` is outside both `fmt-check` and `type`.
- **`S101` is ignored per-file for `tests/**` only.** A global ignore lets a bare `assert` into production masking and auth code, where `python -O` strips it.
- **Pydantic: prefer `AfterValidator` to `BeforeValidator`** for the masked types; the function is then guaranteed a `str`. `Annotated` metadata applies right-to-left, so a `StringConstraints` placed before the masking validator fires against the unmasked value.

## Before implementing

**ZT-2 is the critical path and is answered by another team.** Istio validates the JWT; the domain services must enforce on it. If any handler scopes its query by an account ID from the request body rather than by the token `sub`, the entire authorization layer is decorative and cross-customer access (A5) is live. Finding that out six weeks in is the worst outcome available. The zero-trust plan §7 puts this in week one.

Handoff §10 lists 28 open questions. Several change the architecture rather than the code, and four gate the payment path specifically: headless challenge initiation (§10.4), the app's pairing-code screen (§10.10), where dynamic linking is enforced (§10.13), and whether domain teams will expose pre-masked projections (§10.17). Build all four domains' tool contracts up front but ship payments last, so those four cross-team dependencies do not block reads and tier-1 writes. One of the four has moved since: §10.13 asks whether the app holds a device-bound key that can sign a challenge payload, and this repo has now committed to the answer that it does — `services/confirm` verifies an Ed25519 signature from an enrolled device on every approval and will not start without a key store to verify it against. That is a decision taken here against a dependency the mobile team still has to confirm, not a dependency discharged.

The §5 residual risks in the zero-trust plan are bounded, not closed: client runtime integrity cannot be attested, third-party retention is unrecallable, rendering is outside the operator's control, and the regulatory treatment of consumer AI agents against bank APIs is unsettled. Do not let anyone record them as solved.
