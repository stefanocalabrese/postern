# 0018. Tool families are modules, discovered from installed distributions

Date: 29 September 2026

## Status

Accepted.

## Context

Adding a tool family meant editing source: `services/api/server.py` imported
four modules by name, and `services/confirm/execute.py` held a hand-edited
`TOOL_REGISTRY` of six entries. Extending Postern meant forking it, which is
incompatible with a third party shipping a payments or standing-orders module.

Two constraints bound the design. CLAUDE.md's hard rule -- tool definitions are
static config versioned in the repo, never registered at runtime by backend
services, because runtime registration breaks the PrivateLink design and makes
the surface impossible to diff between deploys. Both clauses bind, and the
second is the one an extension mechanism makes harder. And the read/write key
split, kept by `.importlinter` and by the Dockerfile copying named paths, which
has to survive a module this repo has never seen.

## Decision

**Discovery is Python entry points, resolved at import.** Two groups,
`postern.read_modules` and `postern.write_modules`. `postern_core.modules.groups`
holds the two group-name strings and no types, so the read loader can compare
both groups' distributions without importing the write half.

**A module declares data and one factory, never framework calls.** A `ReadTool`
carries a name, a consent domain, two annotation booleans and a
`build(ReadContext)` returning a plain async handler; `ReadContext` carries the
resolver and the backend reader and nothing else. The host does the `@mcp.tool`
registration, constructs `ToolAnnotations` and wraps the consent check. A
`WriteOperation` carries tool name, audience, path template, method and
verification tier, and no code.

Masked types are deliberately NOT declared. `MaskedPan` and `MaskedIban` mask in
their own constructor, so a module gets masking by using the type; a declared
list would be a field nothing reads.

**One module, two distributions.** `site-packages` is copied whole into both
images, so a single wheel declaring both groups puts backend write routing inside
the read container whatever the Dockerfile copies.
`refuse_distributions_declaring_both_halves` refuses that shape at startup.

**One registration path.** `bootstrap`, `accounts` and `transactions` were
converted to the same `ReadModule` shape; the `cards` family moved out of
`services/` into `postern-cards` and `postern-cards-write`, so the entry-point
path is exercised by shipped code and not only by a fixture.

**The surface is checked in and gated.** `tool-surface.json` is regenerated by
`make tool-surface` from the ASSEMBLED SERVER, not from the declarations, then
cross-checked against them in both directions -- a tool that registered without
declaring fails, and so does a declared tool that never registered. The gate is
not a `ci` dependency, because a target that rewrote the file during `ci` would
make it agree with whatever just happened.

**Trust is documented, not engineered.** A module runs in-process with the
signing key in the same memory and Python offers no boundary. No sandbox, no
permission system, no capability model -- a partial one invites the trust the
warning refuses.

## Why not the alternatives

A registration call from a backend service is what the hard rule forbids: it
needs an inbound path from backend to MCP server, inverting PrivateLink. A
config file listing import paths is read after boot and can differ between
replicas of one image. A database table makes the surface a row an operator can
UPDATE with no diff.

An entry point is a line in an installed distribution's metadata, resolved during
import of the composition root, out of what is baked into the image. Measured
inside the built `api` image: the loader returns the cards module and
`import postern_cards_write` raises `ModuleNotFoundError`.

One honest bound: an entry point is static relative to an IMAGE, not to a
deployment that runs `pip install` at container start. That is an operator
property this repo cannot enforce, and the module-authoring guide says so.

## Consequences

Three enforcement layers, because each is blind to what the next sees.
`.importlinter` gained four contracts, each observed BROKEN by a one-line
mutation before being trusted, and is blind to a distribution outside this tree.
`_refuse_write_half_in_the_read_path` refuses at composition when a read
module's import introduces the write protocol, measured in a subprocess because
the check is relative and one pytest process already imports that protocol; it
is blind to code present but never imported. The Dockerfile plus
`tests/test_module_halves_in_images.py` derives module pairs from
`packages/*/pyproject.toml`, and was checked by hand against all three built
images.

Costs accepted: two distributions per module; `tool-surface.json` must be
regenerated whenever the surface changes, including for a module installed from
outside this repo; the file records declarations and a parameter summary, so a
module whose declaration is stable can be rewritten entirely between two wheel
versions without moving it -- pin modules by hash. `start_session`'s `consents`
list is still literal, so a module adding a fifth domain is absent from it.
`WriteOperation.tier` is read only by the surface file today, because nothing
creates a challenge.

## What a malicious module can do

Everything the process can. Read the signing key by ordinary attribute access,
mint an internal JWT for any audience the process holds a key for, reach any row
its database credential can, monkey-patch masking or consent or audit, open a
socket anywhere egress allows.

What bounds it is not this seam: a module on the read path cannot move money
because that process holds a READ key and the read image does not carry a write
half. The refusals above stop a module CROSSING from read to write; they do
nothing about what it does once it is on a side.

**Installing a module is exactly as consequential as merging a commit into this
repository.** Review it, pin it by hash, build it into your own image.

The quiet failure modes of a careless module, which no gate here catches: a
handler returning a `dict` instead of a masked model leaks whatever the backend
sent that is not PAN- or IBAN-shaped; a tool description is text the model treats
as instruction; a mis-declared consent domain gates a tool on the wrong customer
decision; a module that never records records leaves ZT-5's budget blind to bulk
extraction through it.
