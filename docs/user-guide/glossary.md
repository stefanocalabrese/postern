# Glossary

Key terms and concepts across the Postern platform.

## A

### Anomaly detection
See **Risk Engine**. Per-session evaluation of record budgets, account diversity,
session age, and IP patterns against configurable thresholds.

### ASGI
Asynchronous Server Gateway Interface. The async Python web server interface that
Postern's Starlette/FastMCP stack runs on. Middleware is installed as ASGI layers
wrapping the FastMCP HTTP app.

### ASN
Autonomous System Number. Used for IP-based anomaly detection (currently not wired;
`_suspicious_asn_detected()` always returns `False`).

## C

### Call ID
A UUID that pairs the entry and completion audit rows for a single tool call. Every
audit row carries a `call_id`; rows with the same `call_id` belong to the same call.

### CHECK constraint
A database-level validation rule that enforces closed vocabularies for columns like
`outcome`, `refusal_reason`, and the XOR invariant between `customer_ref` and
`absence_reason`. Enforced by PostgreSQL, not just application code.

### Consent enforcement
Per-tool authorization via a Postgres-backed consent table. `consent_for(domain, db)`
returns an `AuthCheck` that filters the tool catalogue and refuses calls. Refusal
reasons are recorded in the audit log.

### CustomerRef
An opaque customer identifier with pattern `^cust[:_][A-Za-z0-9]{1,60}$` that rejects
IBAN/PAN/national ID shapes at the identity layer. Never a tool argument; never returned
to the client. The token is the identity.

## D

### Device Code
An opaque 40+ character code generated by the RFC 8628 device authorization flow. The
browser polls `/token` with it, and an approved code is exchanged once for a layer-1
session: an access token for the MCP server and a refresh token.

### Device Grant (RFC 8628)
The OAuth 2.0 device authorization grant flow used for QR pairing:

1. Browser calls `/device_authorization` → gets device code + user_code
2. QR code encodes verification URI + pairing code
3. User scans with mobile app → confirms pairing code matches
4. Mobile app approves → browser polls `/token` → a layer-1 session (access token + refresh token)

### Device Code Store
Pluggable backend for device authorization codes. In-memory (dev/test) or Redis
(production). Factory: `create_device_code_store()`.

### Domain Service
The operator's backend services (accounts.svc, payments.svc, cards.svc) that Postern
proxies. domain services must scope queries by the JWT `sub` claim.

## E

### Entry Row
The first of two audit rows per tool call. Written **before** the backend is reached,
with `outcome='reaching'`. Committed in its own transaction via `_PendingEntry` with
an at-most-once guard.

## F

### Fail-closed
A security design principle where failures prevent access rather than allowing it. In
Postern:

- **Fail-closed audit writes**: An audit write failure blocks the call rather than
  allowing unrecorded data access (ADR-0006)
- **Fail-closed masking**: A validation error on `MaskedPan`/`MaskedIban` prevents
  raw value leakage

### FreeText
A Pydantic `Annotated[str, AfterValidator(_redact_free_text)]` type that automatically
redacts PANs and IBANs on validation. Used for fields like transaction remittance info
that may contain embedded card numbers or account details.

## I

### Impossible travel
An IP anomaly detection check: if the client IP changes within a configurable time
window (`impossible_travel_window`, default 300 seconds), a MEDIUM signal is emitted
suggesting the session may be compromised.

### Internal JWT
A short-lived (60-second) RS256-signed token minted by Postern for internal service-to-
service communication. Includes an `act` claim for actor delegation. Verified by Istio
(before domain services return data.

### IP Tracker
Per-session tracker of client IP addresses with timestamps (`time.monotonic()`). Bounded
to 100 entries (FIFO eviction) to prevent unbounded memory growth. Exposes `distinct_ips`,
`last_ip`, and `time_since_last_change()` for anomaly detection.

### Istio
The service mesh that validates JWTs. Domain services must scope queries by the
JWT `sub` claim. Istio JWT validation is **pending**, not yet implemented in this repo.

### JTI Replay Cache
In-memory token replay prevention covering the token lifetime (60-second window). Part
of continuous authorization. Checked after mint to prevent the same token from being
used twice within its validity period.

## J

### JWKS
JSON Web Key Set. Published at `/.well-known/jwks.json` on both the API service (read
key) and confirm service (write key). Unauthenticated endpoint for gateway/client key
discovery.

### Key Split Architecture
Read and write keys are completely separate, published on different JWKS endpoints. A
compromised tool handler cannot mint a token the payments service will accept, because
it does not hold the key. That is an infrastructure property, not a code-review promise.

## M

### MaskedIban
A Pydantic type (`Annotated[str, AfterValidator(_mask_iban)]`) that masks an IBAN to
country code plus last four digits on construction. Counterparty IBANs are omitted
entirely from responses.

### MaskedPan
A Pydantic type (`Annotated[str, AfterValidator(_mask_pan)]`) that masks a PAN to
`•••• NNNN` (four bullets plus last four digits) on construction. Cannot represent a
full PAN.

### MCP
Model Context Protocol. The protocol that gives AI models tools, built for a local,
trusted transport (stdio on a single machine). Postern keeps MCP's tool model exactly as-
is and wraps it in a zero-trust security layer.

### Microsegmentation
The read/write key split architecture: separate JWKS endpoints, separate minters, and
separate deployables (API service vs. confirm service). A compromised read path cannot
reach write endpoints.

## O

### Out-of-band approval
The customer approves a payment on their own device (mobile app), not through the AI
agent. The confirmation payload is built server-side from the stored challenge row, never
from agent input. An injected agent can propose a wrong payee but cannot change what the
customer is shown before they approve.

## P

### PAN
Primary Account Number. The card number on a payment card (12-19 digits). Masked to
`•••• NNNN` by `MaskedPan`. Counterparty PANs are omitted entirely.

### Postern
The zero-trust MCP server that exposes an operator's backend services to AI clients as
tools. Named after a "postern gate", a small, controlled entrance in a fortified wall.

## R

### Read Token Minter
Wraps `InternalTokenMinter` with continuous authorization (revocation check + JTI
replay cache). `READ_SCOPES` maps audiences to read scopes only. `payments.svc` maps
to `payments:read`, for the payee lookup (decision 0022), never `payments:execute`.
The scope is bound to the audience, not to a path, so read tokens cannot reach write
endpoints provided the payments gateway or backend checks the signing key and scope
per path; the minter does not restrict the path.

### Record Count
Immutable snapshot of how many records a session has returned (`RecordCount.total`).
Tracked cumulatively across all tool calls in a session. Used by the risk engine to
enforce `max_records_per_session` (default 500).

### Redis Session Store
Redis-backed session store compatible with AWS ElastiCache, Google Memorystore, Azure
Cache for Redis. Sessions stored as JSON with TTL-based expiry. `_start_time` stored as
wall-clock POSIX timestamp so sessions survive process restarts.

### Refusal Reason
A database-enforced enum column in the audit log: `consent_denied`, `tool_not_found`, or
NULL. Transcribed from the consent module, never inferred by the audit middleware.

### Risk Action
The response to a risk signal: `LOG` (informational), `ESCALATE` (tier escalation), or
`BLOCK` (hard-fail the call). Mapped from `Severity`.

### Risk Context
Per-session state for anomaly detection. Tracksanomaly detection. Tracks records returned, accounts touched,
widest time window requested, session age, IP addresses, and current verification tier.

### Risk Engine
The core component that evaluates that evaluates `RiskContext` against `RiskConfig` thresholds and
emits `RiskSignal`s. Stateless: takes context + config, returns signals. The caller
decides what to do with them.

### Risk Middleware
FastMCP middleware that pushes `RiskContext` onto a ContextVar, records client IPs, and
evaluates signals after each tool call. MEDIUM → escalate tier; HIGH → raise
`RiskActionError`.

### Risk Signal
A structured report from the risk engine: code, description, severity (LOW/MEDIUM/HIGH),
and details dict. Examples: `RECORD_BUDGET_80PCT`, `ACCOUNT_DIVERSITY_EXHAUSTED`.

### Revocation List
Three-scope revocation with O(1) set lookups: per-session (ends that session),
per-customer+client (ends all sessions for a pair), and kill switch (ends ALL sessions
for a client). Pluggable backend — in-memory (dev/test) or Redis (production) — via
`create_revocation_store()`; a production deployment enables `POSTERN_REQUIRE_REDIS` to
refuse startup without `POSTERN_REDIS_URL`.

## S

### Scan Budget
A bounded checksum allowance (100,000 operations per call) for IBAN detection in free
text. Shared across all tokens in one `_redact_free_text` call, not reset per token.
Prevents denial-of-service via adversarial input.

### Session Handle
An opaque identifier passed in tool arguments that links a call to its `RiskContext`.
Created at session start and looked up by the risk middleware on each call.

### Session Store
Pluggable per-session context store with in-memory (dev) and Redis (production) backends.
Factory: `create_session_store()`. Used by the risk engine for tracking session state.

### Severity
The severity level of a risk signal: `LOW` (log only), `MEDIUM` (escalate tier), or
`HIGH` (hard-fail/block). Mapped to a `RiskAction`.

### Startup Minter Probe
A startup-time verification that mints one token and verifies it against the JWKS this
process publishes. Refuses to start if there's a mismatch. Part of workload
attestation).

## T

### Tier Escalation
The process of moving a session to a higher verification tier when the risk engine emits
MEDIUM signals: `SESSION_ONLY` (0) → `APP_APPROVAL` (1) →
`APP_IDENTITY_VERIFICATION` (2). Once at the maximum tier, escalation is a no-op.

### Tool Name Clamping
Agent-controlled tool names are clamped to 64 characters before writing to the audit log,
with a truncation marker (`…`) appended when cut. Prevents `StringDataRightTruncationError`
that would cost the entire audit row under fail-closed policy.

### Two-Row Audit Pattern
Every tool call produces two audit rows (when it reaches the backend): an entry row
(`outcome='reaching'`) before the backend request, and a completion row (`returned` or
`raised`) after. Paired by `call_id`. A consent-denied call produces exactly one row.

## V

### Verification Challenge
A stored record of a proposed write operation (payment, card write). Created when the
model proposes a write via `payments.create_payment`, which is registered only with
`POSTERN_PAYMENTS_ENABLED` on. Contains the payload, tier, and
status. The customer approves on their mobile device; the confirm service executes
server-side from the stored challenge row.

### Verification Tier
Three levels of customer verification:

| Tier | Name | Description |
|------|------|-------------|
| 0 | `SESSION_ONLY` | Session token only. Read operations. |
| 1 | `APP_APPROVAL` | Device-bound key + PIN/biometric. Tier-1 operations. |
| 2 | `APP_IDENTITY_VERIFICATION` | Tier 1 plus server-side selfie matching with liveness. Tier-2 operations. |

## Z

### Zero Trust

Postern's zero-trust controls cover continuous authorization, workload attestation,
key split architecture, per-session anomaly detection, fail-closed auditing, and data
masking. See the [Zero Trust overview](../zero-trust.md) for details on each control
and what is still pending.
