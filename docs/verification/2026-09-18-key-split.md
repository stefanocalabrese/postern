# 2026-09-18: two disjoint key sets, verified against the running stack

Plan 3 (`docs/superpowers/plans/postern-workload-identity-2026-09-16.md`),
Task 6. Tasks 0-5 built the `KeySource` seam, `InternalTokenMinter`, the
read minter in `services/api`, and a minimal `services/confirm` composition
root publishing a write JWKS, all proven in-process
(`tests/test_key_split_is_a_property.py`). This record is the one step that
suite cannot take: bringing up both processes as separate containers and
checking the split over real HTTP, the way an Istio gateway would see it.

## What this is, and what it is not

**No Vault was involved, anywhere in this session.** Both `api` and
`confirm` generated their RSA signing key in process
(`postern_core.auth.keys.GeneratedKeySource`), the same as every existing
`pytest` run and every prior compose session in this repository. The real
Vault integration — `hvac`, AWS IAM auth, lease renewal — is unbuilt, and is
blocked on handoff §10.22 (whether two Vault roles exist) and §10.24
(sidecar versus direct client), per the plan's own "Out of scope,
deliberately" table. Nothing below should be read as having exercised
Vault, a Vault Agent sidecar, or a `FileKeySource` reading a rendered PEM.

**Both services generate a fresh key on every restart, and nothing says
so.** `Settings.read_key_pem_path` and `ConfirmSettings.write_key_pem_path`
both default to `None`; both services' `from_env()` collapse an absent or
empty environment variable to `None` the same way
(`os.environ.get(...) or None`); and `docker-compose.yml` sets neither
`POSTERN_READ_KEY_PEM_PATH` nor `POSTERN_WRITE_KEY_PEM_PATH` on either
service. When the path is `None`, `_read_key_source` / `_write_key_source`
silently return a `GeneratedKeySource` — no exception, no log line, no
startup warning. This record measures the consequence directly (see
"Restart" below): the `kid` string is stable (it comes from a settings
default, not the key), but the key material behind it is not, and an
HTTP client has no way to tell the two apart from the response alone. In a
multi-replica deployment every replica would do the same thing independently
and publish a different key set under the same issuer; that specific claim
is inferred from the single-instance restart result below, not measured
against more than one running replica, because this compose stack never
runs more than one instance of either service.

**Which evidence is which.** Per command below, three kinds appear:
container-to-container HTTP (`curl` against a published port), a direct
write/read against Postgres (`docker compose exec ... psql`, not HTTP), and
a small number of claims sourced from reading a settings or composition-root
file rather than from any request. Each is labelled as it appears.

## 2. `kid` sets are disjoint, and neither entry carries private material — verified over HTTP

Both bodies above, fed through a script that only reads the JSON already
fetched (no new request):

```bash
curl -sS http://localhost:8080/.well-known/jwks.json | uv run python -c "
import json, sys
doc = json.load(sys.stdin)
keys = doc['keys']
print('kids:', {k['kid'] for k in keys})
for k in keys:
    print('private overlap:', set(k) & {'d','p','q','dp','dq','qi'})
print('any write-prefixed kid?', any(k['kid'].startswith('write') for k in keys))
"
```

```
kids: {'read-1'}
private overlap: set()
any write-prefixed kid? False
```

```bash
curl -sS http://localhost:8082/.well-known/jwks.json | uv run python -c "
import json, sys
doc = json.load(sys.stdin)
keys = doc['keys']
print('kids:', {k['kid'] for k in keys})
for k in keys:
    print('private overlap:', set(k) & {'d','p','q','dp','dq','qi'})
print('any read-prefixed kid?', any(k['kid'].startswith('read') for k in keys))
"
```

```
kids: {'write-1'}
private overlap: set()
any read-prefixed kid? False
```

`{'read-1'}.isdisjoint({'write-1'})` is trivially true. Every entry's key
set (`{n, e, kty, alg, use, kid}`) carries no `d`, `p`, `q`, `dp`, `dq` or
`qi` on either side — the private RSA parameters `joserfc`'s `as_dict()`
only emits under `private=True` (Plan 3's own "Verified facts" section),
which neither `jwks_route` handler requests.

## 3. Neither service serves the other's key — verified over HTTP

Same two response bodies as above answer this directly: the api's JWKS
(port 8080) contains only `read-1` and no `kid` beginning `write`; the
confirm service's JWKS (port 8082) contains only `write-1` and no `kid`
beginning `read`. No separate endpoint exists on either service to probe —
confirmed by reading `services/api/main.py` and `services/confirm/main.py`
(file read, not HTTP): each appends exactly one route
(`app.router.routes.append(jwks_route(...))` / `Starlette(routes=[jwks_route(...)])`)
to an app that otherwise serves `/mcp` (api) or nothing else at all
(confirm), so there is no combined or alternate JWKS path to accidentally
hit instead.

## No defect found

The compose addition, the `confirm` build target, and both JWKS routes
behaved exactly as `services/confirm/main.py`, `services/api/main.py`,
`services/confirm/jwks.py` and `services/api/jwks.py` already described.
Nothing needed to be changed in application code to make this record's
checks pass; the only repository change this task made is the
`docker-compose.yml` service block itself.

One naming note, not a defect: the plan's own draft pseudocode (Task 4,
Task 1) used `https://mcp-read.bank.internal` / `https://mcp-write.bank.internal`
as example issuer strings. The shipped defaults in
`services/api/settings.py` and `services/confirm/settings.py` are
`https://mcp-read.internal` and `https://mcp-write.internal` (no `.bank`
segment) — consistent with `fb1a5ee`'s repo-wide removal of the
bank-operator framing from the code, which post-dates the plan's draft.
Neither string was asserted anywhere in this record; noted here only so a
future reader comparing this file against the plan's own code blocks does
not read the difference as a discrepancy this session missed.

## What was not, and could not be, verified this way

- [ ] **Vault was not exercised, at all, by design.** `FileKeySource` (the
  shape a Vault Agent sidecar renders a PEM into) was not driven, because no
  Vault or Vault Agent runs in this stack. Nothing here says anything about
  whether Vault actually holds two roles keyed to two paths, whether a
  sidecar can render a PEM at all, or what happens when the file it renders
  changes on disk under a running process. Blocked on handoff §10.22 and
  §10.24, unchanged by this session.
- [ ] **Key rotation was not exercised.** The restart in section 4 shows a
  full key *replacement* on process restart, not a rotation with an overlap
  window where two keys are simultaneously valid under one `kid`-keyed
  lookup. `KeySet` selecting by `kid` is proven in-process
  (`tests/test_key_sources.py`), not against a rotation event here.
- [ ] **No Istio, no `RequestAuthentication`, no `AuthorizationPolicy` was
  run.** Every "the write endpoint accepts/rejects this" claim in the
  in-process test suite (`tests/test_key_split_is_a_property.py`) simulates
  what a gateway does (`istio_write_endpoint`, a hand-written `jwt.decode` +
  `JWTClaimsRegistry` check); this record's HTTP checks stop at fetching the
  two JWKS documents and calling `/mcp`, and touch no gateway of any kind.
  Whether a real Istio `RequestAuthentication` can or cannot bind two
  issuers to one `jwksUri` — the platform-team question the plan's D1 decision
  is contingent on — is not answered by anything in this repository.
- [ ] **Multi-replica behavior is inferred, not measured.** This compose
  stack never runs more than one instance of `api` or `confirm`
  simultaneously, so "every replica would publish a different key set under
  the same issuer" is a direct consequence of the restart-generates-a-new-key
  behavior measured in section 4, not an independent observation of two
  concurrently running replicas disagreeing with each other.
- [ ] **`act.sub` enforcement, and every other Istio-side claim check, is
  out of repo.** Unchanged from the plan's own "What this plan deliberately
  does not establish" table; this record adds nothing to that line.
- [ ] **The IAM policy test — the read task role cannot assume the write
  role or read its Vault path — was not run.** That is Terraform-repo
  scope, not expressible here; it is a CI gate the zero-trust plan's
  product-specification sections list (§4, work item ZT-3's acceptance
  criterion; §6.1's blocking-gates table), not this repository's deployment
  status, and it stays unanswered by anything in this session.
- [ ] **Ownership/ZT-2 enforcement is not exercised by the tool call in
  section 5, for the same reason every other record in this directory
  states it isn't**: `stub/backend.py`'s `accounts` route filters by the
  token subject (post `316b51c`), but section 5 asks only "does the
  response still come back masked with the new minter wired in," not
  "does the real operator backend enforce on `sub`" — that answer belongs to
  another team and is not in this repository.
